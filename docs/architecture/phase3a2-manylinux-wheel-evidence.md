# Phase-3A2 wheel and same-wheel evidence contract

Status: accepted implementation contract; package, workflow, and runtime evidence
pending.

This record is the operational companion to [ADR 0014 — pinned manylinux wheel
evidence](../adr/0014-phase3a2-pinned-manylinux-wheel-evidence.md). It is a
private helper boundary, not a Matplotlib backend or a release workflow. The
public v1 adapter, Matplotlib Artist authority, fallback profiles, and
Phase-3B compatibility matrix remain open under [API 0003](api-0003-python-numpy-matplotlib.md).

## Claim boundary

The only permitted Phase-3A2 claim is:

> One privately named `lumenplot-mpl` wheel with tag
> `cp311-abi3-manylinux_2_28_x86_64` was built from the reviewed locked source
> in the reviewed x86_64 glibc-2.28 builder and the identical wheel passed the
> declared private-helper fixtures in explicit GIL CPython 3.11, 3.12, 3.13,
> and 3.14 environments.

This claim is not any of the following:

- a Matplotlib backend, `module://` entry point, or public `render_png` API;
- a support commitment for Python, NumPy, Matplotlib, Linux, or another OS;
- evidence for the standard Figure/Artist profile or any Phase-3B profile;
- a publication, signing, deployment, or release result;
- a Scene, RenderPacket, wheel, or CI-JSON persistence format.

The private Python surface is `lumenplot_mpl._native.render_line_png` and its
structured `LumenPlotError` mapping. A public `lumenplot_mpl.backend` module is
intentionally absent from this slice.

## Activation and checker behavior

`python3 scripts/check_workspace_architecture.py` keeps the current Rust
baseline unchanged until one implementation sentinel appears:

- root `pyproject.toml`;
- `python/lumenplot_mpl/`;
- a workflow containing a wheel/manylinux/maturin/auditwheel path; or
- a `pyo3` or `numpy` runtime dependency in `crates/lumenplot-python/Cargo.toml`.

After activation the default checker fails closed on the exact private package
layout, PyO3/Rust-NumPy dependency specifications, direct container workflow,
action inventory, immutable inputs, and four-cell static contract. It does not
claim runtime evidence. The dedicated Phase-3A2 workflow invokes the explicit
`--phase3a2-evidence` mode only after generating the CI-local manifest; that
mode additionally requires and validates the manifest. The manifest is
generated by CI and must not be committed to this public repository. Missing
or malformed evidence in explicit mode is failure, not an unmeasured pass.

The checker is deliberately standard-library-only. It reports repository-
relative diagnostics and never prints runner paths, task identifiers,
credentials, or raw artifact paths.

## Direct builder workflow

The workflow is an explicit direct-container procedure. It must not delegate
building to `PyO3/maturin-action`, `actions/setup-python`, a host interpreter,
or an unpinned image. The job has `push` and `pull_request` coverage for
`main`, workflow-level `contents: read`, no secrets, no `pull_request_target`,
no package write permission, and no publication/signing/deploy step.

The prefetch container is the only networked phase and uses `--network=bridge`.
It downloads only the reviewed inputs into a job-local wheelhouse; no cross-run
cache is used. The
build, audit, and runtime containers use `--network=none`, so a successful
result cannot hide an undeclared network fetch. Both phases use the exact image
above, `--platform=linux/amd64`, `--read-only`, an explicit non-root `--user`,
`--cap-drop=ALL`, `--security-opt=no-new-privileges`, read-only source and
wheelhouse mounts, and `--tmpfs` for temporary writable state. The source
checkout is never mounted read-write; `--privileged` and host networking are
forbidden.

The workflow command shape includes equivalent checks to the following:

```text
docker pull --platform=linux/amd64 <exact-tag@digest>
docker image inspect <exact-tag@digest>
docker run --rm --platform=linux/amd64 --network=bridge --read-only \
  --user <uid:gid> --cap-drop=ALL --security-opt=no-new-privileges \
  --tmpfs /tmp --mount <source-read-only> --mount <wheelhouse> \
  <exact-tag@digest> /bin/bash -eu -o pipefail -c '
    export RUSTUP_TOOLCHAIN=1.89.0
    rustc --version
    cargo --version
    cargo fetch --locked
    cargo metadata --locked --format-version 1
  '
docker run --rm --platform=linux/amd64 --network=none --read-only \
  --user <uid:gid> --cap-drop=ALL --security-opt=no-new-privileges \
  --tmpfs /tmp --mount <source-read-only> --mount <wheelhouse> \
  <exact-tag@digest> /bin/bash -eu -o pipefail -c '
    maturin==1.14.1
    cargo build --release --locked --offline
    auditwheel show --json <wheel>
    auditwheel check <wheel>
    readelf -d <native-object>  # reject RPATH and RUNPATH
    abi3audit <wheel>
  '
```

`auditwheel repair` is forbidden. Repair would create a second, unrecorded
artifact and invalidate the same-wheel identity. The workflow must use
`--locked --offline` for the build and record the Cargo lock SHA-256, source
checksum/license results, and SBOM input set.

## Wheel checks

A passing run must record these independent true booleans:

- ZIP integrity;
- `METADATA` version equals the Cargo-derived version;
- `WHEEL` contains exactly `cp311-abi3-manylinux_2_28_x86_64`;
- every `RECORD` hash and size is correct;
- ELF dependencies and RPATH/RUNPATH are acceptable;
- `abi3audit` accepts the CPython abi3 surface and no `abi3t` appears;
- the private-helper fixtures pass in every runtime cell;
- the SBOM and locked source/checksum/license set are present; and
- evidence redaction and ownership checks pass.

The run executes `auditwheel show`/`auditwheel check`, `readelf -d`, and
`abi3audit`; it does not repair or silently rewrite the wheel. Optional CI artifact upload is evidence storage only and must use a full action
SHA, run only for a trusted push to `main`, set `if-no-files-found: error`, and
retain the evidence for exactly seven days. The first implementation may omit
upload.

## CI-local evidence manifest schema

`phase3a2-wheel-evidence.json` is generated under CI-only workspace storage. It
must be UTF-8, LF-ended, two-space, lexicographically sorted exact-key JSON, and
must not be committed. Its schema identifier is exactly
`lumenplot.phase3a2-wheel-evidence.v1`; runtime cells are ordered 3.11, 3.12,
3.13, 3.14. It contains no
absolute runner paths (`/home/`, `/tmp/`, or host user paths), credentials,
secrets, task/session identifiers, or raw internal artifact paths.

The exact top-level object is:

```text
{
  "builder": {...},
  "checks": {...},
  "claim_boundary": {...},
  "runtime_cells": [...],
  "schema": "lumenplot.phase3a2-wheel-evidence.v1",
  "source": {...},
  "wheel": {...}
}
```

Required shapes and values are:

- `source`: `commit` (40 lowercase hex), `cargo_lock_sha256` (64 lowercase
  hex), `distribution: "lumenplot-mpl"`, `cargo_version`;
- `builder`: exact image/tag+digest, image config digest, `platform:
  "linux/amd64"`, `glibc: "2.28"`, `auditwheel_version: "6.8.0"`,
  `abi3audit_version: "0.0.26"`, `rust_version: "1.89.0"`,
  `maturin_version: "1.14.1"`, and the accepted maturin wheel SHA-256;
- `wheel`: exact filename/tag, a 64-hex SHA-256, Cargo and `METADATA` versions,
  and true `zip`, `metadata`, `wheel`, `record`, `elf`, `abi3`, and `sbom` flags;
  `sbom_format` is exactly `CycloneDX 1.5`, verified against Cargo metadata/lock;
- `runtime_cells`: exactly four exact-key objects for Python 3.11–3.14, with
  explicit interpreter, NumPy `2.4.6`/hash, identical and rechecked input-wheel
  hash, Cargo expected version, installed distribution version, and `result: "pass"`;
- `checks`: exactly these true booleans: `cargo_locked_sources_checksums_licenses`,
  `same_wheel`, `metadata_version`, `auditwheel`, `elf_rpath`, `abi3audit`,
  `private_helper_fixtures`, and `redaction_ownership`; and
- `claim_boundary`: exactly `private_helper_only: true`,
  `release_artifact: false`, `platform_support_claim: false`, and
  `publication_authorized: false`.

A generated manifest is evidence for one named run. It is not a public schema,
serialization format, package metadata source, or release artifact.
